00 / THE BIG PICTURE

Harness 是什么，它真正管理什么？

Harness 是包围模型的执行与协调系统。模型负责在当前输入下生成下一步；harness 负责准备输入、执行工具、保存状态、处理权限与中断，再把结果交回模型。

核心判断：一个可用的 agent，依赖“模型能力 × 上下文质量 × 执行可靠性 × 外部反馈”。只调整提示词，无法补齐持久化、工具隔离和恢复语义。架构分析

四个平面：交互、控制、执行、状态公开实现 + 抽象整理

模型通常不会直接持有电脑和数据库的句柄。它输出结构化动作，由宿主选择并执行。公开 Codex 将核心执行能力通过 app-server 暴露给不同客户端。[D1][D2]

贯穿本报告的模型是：历史是证据账本，上下文是工作台，记忆是索引与提炼，工作区是成果与事实所在。它们之间需要显式的读写和同步规则。

01 / PROMPT AS A COMPILED POLICY

系统提示词：把工作规范编译成模型可执行的约束

实际工程中，“系统提示词”往往是多来源上下文的装配结果。基础行为、产品约定、项目规则、工具协议与当前环境，各有不同更新频率和可信度。

1.1 逻辑：分层、按需、明确冲突规则

高层指令规定角色、持续工作方式和权限边界；项目指令补充构建命令、目录习惯和验收要求；当前任务给出目标和局部约束；工具结果提供事实。将这些内容混成一段无来源的文本，会让模型难以区分“应该遵守什么”和“只是看到了什么”。

公开源码的 render_model_instructions 从已解析的模型元数据读取模板；独立的提示词模块处理权限、多 agent、模式等片段。模型和客户端可以有不同模板，不能用某个历史版本的 Markdown 文件代表所有运行配置。[C1]

输入：模型配置、当前模式、权限快照、项目规则、技能目录、工具目录、环境信息与活动历史。

输出：带角色与结构化内容的请求，不只是一个长字符串。工具 schema、call ID、消息 phase 等也属于行为协议。

1.3 好的提示词需要把模糊口号变成决策条件

设计点可执行的写法思路为什么有用
持续推进动作请求应完成实现、适当验证和交付；缺少关键条件时记录阻塞减少“只给计划”“工具回来就结束”等提前停止

上下文节制先定位再局部读取；大型输出保存为产物并返回摘要与入口减少低价值 token，保留可继续调查的路径
信任边界外部页面、日志和子 agent 消息带来源，不能自行升级为用户授权降低提示注入与授权误传
交互协议明确进度与最终答案、调用与结果、成功与待处理的区别UI 与控制循环能正确识别生命周期

优点

修改成本低、易于表达语义规则；能随模型调整；项目与技能可组合；可通过行为评测快速迭代。

缺点与失效方式

规则越多越容易冲突；长模板消耗预算并稀释任务；模型遵守是概率行为。安全和一致性不能完全交给语言约束。

工程边界：“不要越权”写在提示词里是软约束；文件写入限制、工具白名单和审批状态机才是宿主执行的硬边界。配置“永不询问审批”也不等于获得无限文件或网络权限。

02 / THE EXECUTION ENGINE

Runtime：把输出变成动作，再把世界的反馈交回模型

一次用户请求可以包含许多次模型请求和工具执行。Runtime 管理这个回合的推进，并处理用户插入的新信息、异步结果、取消与失败。

公开代码的回合循环会结合模型继续标记和待处理输入决定是否继续，并在循环中检查自动压缩。此图省略重试、hooks、审批和异常分支。[C2]

2.1 数据模型：Thread → Turn → Item

Thread 是可持续的对话容器；Turn 是一次用户请求及后续工作；Item 是消息、工具调用、命令执行、文件变更等输入输出单位。一次模型推理请求只是 turn 内的一步。由这些层次生成进度事件，UI 才能展示“正在运行工具”，并在真正完成时关闭回合。[D2]

控制面：app-server

连接先完成初始化握手，再建立或恢复线程，通过回合方法驱动工作，接收 item 与 turn 事件。客户端、核心执行逻辑和展示因此解耦；CLI、IDE 和桌面可以复用核心能力。

接口示例见第 04 章。具体传输与字段需以对应版本的 app-server schema 为准。

执行面：宿主和工具 Runtime

工具路由器解析模型的结构化调用，将参数映射到执行器；执行器处理权限、工作目录、超时和输出。长命令可返回进程会话句柄，随后读取输出；句柄是执行器状态，不能只从聊天文本恢复。

2.2 调度中的几个关键选择

  • 并行与串行：独立读取可以并发；修改同一资源、依赖上一步结果、授权判断应按顺序处理。并行工具调用不等于多 agent；前者仍可由一个模型上下文发起。
  • 流式与最终态：增量文本先展示，完成的 item 再进入规范记录。应保留消息类型和 phase 等元数据，避免恢复时把进度当作最终交付。[D4]
  • 插入新输入：用户 steering 需要进入当前任务的待处理输入；取消应传播到模型流、工具和子任务，而不能只让 UI 停止动画。
  • 重试：网络读取和模型流可以重试，但带副作用的调用必须识别“已执行、响应丢失”的情况。通用分布式系统设计需要操作 ID、幂等键或执行前查询，不能假设所有工具恰好执行一次。
  • 输出治理：原始工具结果可以很大，模型需要的是可消费结果。截断应保留错误原因、总量、产物入口与查询方式。

2.3 具体 Runtime：异步宿主与程序化工具层

公开 Codex 核心以 Rust 实现，使用 Tokio 的任务、channel、watch 和取消机制组织异步工作。线程管理器保存可加载的线程对象；模型适配器处理流；工具执行器负责实际动作；记录器和扩展通过明确边界接入。这里的 runtime 包含任务系统与协议适配，不只是一个解释器。

在启用 Code Mode 的路径中，模型可生成 JavaScript，把多个工具调用组合成程序。公开工具描述定义了每个执行单元使用新的 V8 isolate，并通过宿主暴露的工具委托访问能力；它不是任意 Node.js 环境，也不直接拥有文件和网络 API。执行单元结束会释放 isolate，跨单元保留的数据需要显式存储机制。长执行有执行、让出、等待和终止等协议；宿主可通过进程或远端 provider 管理这层运行环境。[C12]

// 程序化工具编排示意；工具名和输出函数随环境而异
const results = await Promise.all([
  tools.read_file({ path: "module-a.ts" }),
  tools.read_file({ path: "module-b.ts" })
]);
// 在执行层筛选和聚合，只把当前判断需要的结果返回给模型。
// 原始工具证据仍应通过 Runtime 记录或产物入口保留。

它能减少“模型调用 → 一个工具 → 模型调用”的往返次数，并避免让所有中间数据进入主模型上下文；代价是代码执行失败、未等待 promise、预算超限与取消传播都需要额外处理。程序化工具调用、持久 REPL、shell 进程和主 agent 的活动窗口，各有独立生命周期，不能当作同一块内存。

优点

把复杂任务变成可观察的闭环；工具错误提供纠偏信号；模型与执行器可以独立升级；多客户端可共享同一协议。

成本与局限

状态、事件、持久化和 UI 容易不同步；重试可能重复副作用；长工具、断连和后台进程带来恢复难题。异步越多，越需要明确所有权和取消语义。

03 / CONTEXT ENGINEERING · FOCUS

上下文管理：决定模型这一刻能“看见”什么

上下文不是聊天记录的同义词。它是 harness 为下一次推理构造的有限输入视图：稳定规则、当前状态、近期工作，以及从旧历史中保留下来的信息。

3.1 一个实用的上下文装配模型

本次请求 ≈ 基础指令 + 工具目录 + 项目/环境片段 + 保留历史或压缩状态 + 最近交互 + 本次新输入

这只是逻辑拆分。实际序列化格式、服务端注入内容和模型计数方式会影响 token 数；某些配置由顶层参数表达，某些由消息表达。图片、音频、工具 schema、推理和加密项也不能按普通字符数精确换算。

公开源码 中，ContextManager 持有带元数据的 response item 列表、token 信息、上下文基线和保留事实。请求前会规范化工具调用与结果、移除孤立输出，并处理不支持的模态。该快照还把部分宿主保留事实与模型活动窗口分开存储。[C3]

记忆与项目规则索引、摘要、适用范围

3.2 预算管理：留出“继续工作”的空间

不能等到窗口完全装满才压缩。下一步可能产生工具输出，模型还需要生成和推理的空间；压缩请求自身也要能处理待压缩输入。因此应设置低于硬上限的触发阈值，并在大输入加入前、连续执行中、模型切换到较小窗口时检查。

3.3 三种“减小上下文”不能混为一谈

方式做法保留能力主要风险
截断 / 裁剪减少单条工具输出，移除旧项或不支持的模态直接降低体积；原始产物可另存截掉关键错误、授权或精确值；破坏 call/result 配对
语义压缩 / Compaction把旧窗口重写为更小的可续接状态，可能保留部分原始项继续原任务，不必从零开始细节丢失、错误结论固化、压缩开销与缓存失配
检索 / 按需读取只引入当下相关的文件片段、历史或外部证据可以回到原证据恢复精度漏检、查询偏差、权限与时效不一致

合理组合是：先在来源处控制输出，再用检索维持精确度，用压缩保存连续工作状态。无限制地把文件或网页全文塞进上下文，既昂贵，也会让重要约束淹没在噪声中。

3.4 Compaction 的两条路径

公开 harness 的文本摘要路径

源码保留摘要提示、用户消息筛选和替换历史逻辑。压缩后以较小历史继续，必要时重注入当前配置与环境。该路径便于理解和诊断，但摘要可能漏掉精确细节。

core/src/compact.rs[C4]

模型服务支持的压缩路径

公开实现还存在远端压缩路径。Responses API 文档描述不透明的加密压缩项及保留项；这类状态应按协议原样续传，不能把它当成可以编辑的自然语言摘要。

compact_remote_v2*[C4][D6]

两条路径说明“压缩”是接口与状态变换，不等于固定的一段摘要文本。API 的独立 compact 接口返回的是后续窗口；当前文档要求保留它返回的完整输出，而非只摘出一个加密项。具体 Codex 使用哪种路径，应查看对应模型、provider 和 feature flags。

3.5 一个可靠的压缩检查点应该留下什么？

  • 目标：用户真正要完成的事，后续变更与明确撤销。
  • 约束：允许的操作、目录或分支范围、必须遵守的条件。
  • 事实：已经验证的结果、证据位置、文件与调用标识。
  • 工作状态：已完成、尚未完成、失败原因、下一步。
  • 不确定性：假设、未验证结论、可能过期的观察。
  • 协议状态：窗口编号、配置基线、版本、必要的来源与恢复元数据。
# 通用检查点示例
objective: 修复支付重试中的重复写入
scope: services/payments, branch fix/retry
constraints:
  - 用户要求保留现有公开 API
verified:
  - 重试路径缺失幂等键；证据 retry.ts:87
  - 最小复现保存在 artifacts/repro.json
completed:
  - 已完成复现；尚未改生产代码

  - 读取 repository.ts 的写入路径

上例为设计建议 它强调“可继续工作所需状态”，并非完整思维过程的备份。压缩存在语义损失，不能保证任意旧细节都可由摘要还原；关键数字、原文和授权证据应保留可追溯入口。

3.6 后台压缩最难的地方：并发一致性

若压缩在后台运行，主线程可能继续收到用户纠正和新工具结果。一个基于旧窗口生成的候选检查点，不能覆盖新状态。通用做法是给历史增加版本号，记录候选的输入边界，安装前验证可兼容性，保留边界之后的新增后缀，不符合条件则放弃候选或转前台压缩。

源码可见 后台压缩候选、安装逻辑和历史修订字段，以及相关的恢复与并发测试；这表明 compaction 不只是一次“总结对话”的模型调用，还涉及宿主的状态替换协议。[C3][C4]

3.7 缓存：减少重复计算，不改变上下文容量

稳定的规则、工具定义和历史前缀，有助于命中服务端 prompt cache。把每次变化的时间戳、工具顺序和无关环境信息放到前缀中间，会导致较早的位置发生变化，减少可复用前缀。压缩也会改变历史，所以应同时衡量输入体积、缓存复用和任务质量。[D7]

三个常见误解：缓存命中不会让模型“额外记得”窗口外的内容；保存 thread ID 不保证保留原推理进程或 KV cache；较大的窗口也不自动解决相关性、噪声和过期事实问题。

3.8 上下文工程的收益与代价

收益

允许任务轨迹超过单个窗口；主线程保留目标与关键决策；结合外部证据可以恢复精确度；预算可预测、输出更易审查。

代价

压缩增加延迟与调用成本；摘要可能失真；反复压缩会累计语义损失；裁剪、模态和工具协议兼容性复杂；需要专门评测恢复后的任务表现。

04 / DURABLE CONVERSATIONS · FOCUS

历史会话管理：账本、投影、检查点与分叉

会话持久化的目标，是能解释发生过什么，并在以后继续工作。恢复必须同时考虑模型历史、当前配置和真实工作区；重新显示聊天气泡只完成了其中一部分。

4.2 事件账本与可查询视图，为什么要同时存在？

从逻辑上，可以把会话存储理解为“有顺序的规范记录 + 可重建的查询投影”。JSONL 适合追加、检查和逐条回放；SQLite 适合列表、筛选、分页和跨字段查询。新版源码的物化过程从上次偏移读取完整记录批次，并更新投影检查点，不必每次重做全量解析。

两者共存会产生一致性问题：文件可能已经写入而投影尚未更新，UI 缓存也可能滞后。工程上应以完整记录边界推进投影，保存来源位置和修订信息；发现缺失或版本不兼容时修复投影。源码中的读取修订检查、物化和列表修复路径体现了这种思路，而非简单把两个存储分别写一遍。

4.4 Resume、Fork、Revert、Archive 各改变什么？

操作对话语义存储 / Runtime工作区边界
Read / List查看已有记录可分页读取；无需激活模型循环不代表继续执行
Resume在原线程继续加载状态和最新模型窗口，重新建立所需能力恢复时文件可能已变化；需要核对
Fork从选定历史边界创建新线程新 ID、继承前缀、新后缀；新版可通过 lineage 引用冻结边界不会天然创建独立目录、分支或沙箱
Revert移除指定回合及其后续可见历史该快照可保持 thread ID，并切换到新 rollout 修订不撤销文件修改或外部 API 的副作用
Archive将历史归档，默认列表隐藏仍保留恢复与读取入口；具体产品生命周期各异归档记录不等于清理工作区
Ephemeral临时会话 / 临时分叉支持不加入持久线程历史的内存模式文件和外部系统仍可能留下执行结果

接口参考当前 app-server 文档；分叉和修订实现参考 thread-store。当前文档已用 thread/revert，并标明旧 thread/rollback 已移除，不能直接复制旧教程。[D2][C8]

4.5 分叉实现：冻结前缀，不让父线程后来的工作渗入

概念上 fork 是“复制历史”，实现上未必复制所有字节。新版公开代码保存 history_base，其中含来源记录序号和字节截止位置；lineage 表示祖先片段。分叉时先持久化来源，再确定边界，子线程沿该冻结前缀读取自己的继承历史。父线程继续产生的新记录不属于子线程前缀。

4.6 恢复时最容易漏掉的五类状态

  1. 真实环境漂移：文件、分支、依赖或外部记录可能已改变。应重新读取当前状态，对旧测试结果保留版本标识。
  2. 未完成调用：恢复看到已发起工具调用，却没有结果，不能直接认定未执行。读操作可重试，写操作应查业务操作 ID 或幂等结果。
  3. 授权与来源：旧摘要里的“用户同意”可能缺少条件和范围；不能把 agent 自己的提议升级成授权事实。
  4. 配置与能力：模型、工具 schema、凭据、MCP 可达性和权限可能变化。当前可执行能力必须重新解析；不应该把旧工具句柄当作新能力。
  5. 活动资源：后台 shell、连接与内存队列的恢复能力取决于宿主服务。只有保存聊天记录，无法保证它们仍存活。

4.7 UI 历史、模型历史和诊断历史应分别建模

UI 需要可读的消息、命令和文件变更；模型需要协议合法、预算受控的 items；调试需要请求、工具执行和事件的因果关联。三者强行共用一份“聊天字符串”，会出现重复消息、缺失调用关系、恢复后 phase 丢失、以及“工具执行了但模型没看到结果”等问题。

公开 rollout-trace 用原始事件和 payload 引用，再由 reducer 生成图，明确区分模型可见内容和 Runtime 对象。例如程序化工具调用可能执行多个嵌套工具，主模型只看见外层代码调用和主动输出的结果，不能从 UI 摘要反推模型读到了所有原始返回值。该 trace 需显式启用，不能与默认持久会话记录混同。[C12]

这种架构的优势

恢复可被检查点约束；完整证据可追溯；UI 可分页；fork 能保存分支语义；持久记录可重建查询投影。

需要承担的代价

格式迁移、双层存储一致性、祖先 lineage 生命周期、检查点兼容和损坏修复都较复杂。旧模型结论与新环境之间还存在语义一致性问题。

05 / MEMORY WITH PROVENANCE

长短期记忆：从工作状态，到可复用的历史证据

“记住了”至少有三种含义：还在当前窗口里、可以从历史中查到、已经被提炼为跨会话记忆。它们的可靠性、成本和更新方式完全不同。

5.1 用生命周期划分记忆

类型典型载体适合保存不宜依赖它保存
短期 / 工作记忆活动窗口、近期工具结果、当前计划与压缩状态当前任务的目标、约束、发现和待办无限期保留的所有日志、任意精确原文
情景记忆 / 任务历史rollout、回合记录、每次任务摘要做过什么、何时做、证据在哪、结果如何不经筛选就作为全局长期规则
长期派生记忆记忆摘要、索引、主题文件、检索工具重复有用的决策、明确偏好、适用范围和证据入口当前生产状态、临时授权、已经失效的工具结果
显式项目知识AGENTS.md、文档、技能、测试团队可审阅的规范与可执行流程未经确认的个人推断、隐含跨项目偏好

压缩解决“同一任务继续工作”，长期记忆解决“未来任务复用经验”。压缩窗口再大也不等于长期记忆；将完整历史保存到数据库，也不会自动变成有效检索。

5.2 Codex 公开记忆管线：提取与整合分开

源码存在两阶段管线：符合条件的根会话启动后，后台选择历史 rollout；Phase 1 对各任务提取结构化结果并写入状态存储，Phase 2 在全局锁下整合并更新记忆文件。它受 feature flag、会话类型、状态库、配额和配置限制，不能据此断言所有用户默认都启用。[C9]

5.3 版本差异：不能把 V1 布局当成永久架构

V1：摘要 → 注册表 → 证据

源码读提示使用 memory_summary.md 作为轻量入口，配合 MEMORY.md、rollout_summaries/ 和技能目录逐步深入。Phase 1 可生成 raw_memory 与任务摘要，整合阶段组织更高层输出。

V2：更强调真实任务与人类证据

当前快照同时存在 memories_v2 独立命名空间。V2 提取 schema 仅含任务摘要和 slug，提示强调用户原始请求、纠正、范围、时间顺序、未完成工作与证据，而不是把一次对话过度泛化成人格偏好。

读取扩展将精简摘要作为上下文片段注入；该快照的摘要预算为 2,500 近似 tokens。启用专用记忆工具时，还提供 list/search/read 等检索接口；否则可存在基于文件的读取路径。这里的数值是公开快照中的实现常量，不代表稳定产品承诺。没有证据说明这条本地路径必须使用向量数据库；文件搜索和分层索引本身就能构成记忆系统。[C10]

5.4 什么值得记，什么应该被遗忘？

通用设计 一条记忆至少应携带内容、来源、适用范围、生成时间、验证时间与不确定性。优先保存能改变未来行动的稳定信息；临时日志和一次性错误不应无限积累。对于“用户这次要求先给计划”，应记为当前任务条件；只有用户明确表达长期偏好时，才推广为跨任务偏好。

# 建议的数据形态，不是 Codex 的固定 schema
content: 支付模块当前使用应用层幂等键
scope: repository-X / services/payments
source: rollout-T7 + commit abc123
kind: observed_project_decision
valid_at: 2026-10-20
confidence: observed
verification: 变更前读取当前 repository 实现
supersedes: old-note-17
status: active

遗忘不只是 TTL 到期删除。需要区分“不再注入”“不再参与整合”“删除派生摘要”“删除原始证据与备份”。公开管线按使用时间和使用情况筛选整合输入，并存在清理与显式更正入口，但这些选择不应被解释为对所有历史数据的自动彻底删除保证。

5.5 写入路径：显式纠正也应保留来源

当前公开读取提示要求显式的 remember / forget / correction 写入小型 ad hoc note，由整合管线更新生成文件，而不是直接随手改生成记忆。后台自动提取与当前任务内显式记忆修改是两条不同路径。这样便于追踪“谁要求改变什么”，也减少手工修改下一次被生成器覆盖的问题。

记忆整合 agent 的能力也应受限：公开代码的托管权限路径将写入限制在记忆目录并关闭网络，且控制递归协作；父配置显式禁用托管沙箱或使用外部权限模式时，则走继承分支，不能把这个隔离范围视为无条件保证。把历史文本作为证据输入，而不是允许它决定工具权限，是隔离记忆污染的重要边界。[C9][C10]

收益

减少重复探索；保留项目决策；跨会话保持一致；精简入口降低启动成本；有出处的记忆可以复核。

风险与成本

过度概括、过期事实、跨项目串味、自我强化和提示注入；提取与整合消耗 token；需要更新、纠错、删除和访问控制。

最重要的原则：记忆是历史线索。当前指令决定任务，当前拥有者数据决定事实；有变动风险时应回到原始来源验证。

06 / TOOLS ACROSS A PROTOCOL BOUNDARY

MCP：连接外部能力的协议，执行仍由 Harness 管理

MCP 让宿主以统一协议发现和调用外部工具、读取资源。它不自动提供长期记忆，也不保证外部数据可信，更不替应用完成所有权限判断。

6.1 三个角色与两类连接

Host 是 Codex 这类应用；它管理模型、用户授权和工具可见性。MCP Client 是宿主内部的协议连接组件；Server 提供工具与资源，并连接真正的业务系统。模型看到工具描述和参数 schema，输出调用意图，宿主将它转成 MCP 请求。

STDIO / 本地服务

宿主启动服务进程，通过标准输入输出交换协议消息。适合本地文件、开发工具和私有适配器；需管理进程、环境变量、工作目录和生命周期。

Streamable HTTP / 远程服务

Client 访问远程端点，处理网络、认证、会话和重连。Codex 文档支持配置 URL、认证与超时；OAuth 登录是宿主与服务之间的流程，不需要把凭据放进模型提示词。

6.2 公开连接管理器做了哪些工作？

源码 McpConnectionSet 聚合连接，维护启动状态、服务元数据、工具与资源目录。它位于 McpRuntime / McpBinding 之后，包含连接身份比较、可复用 client、目录缓存和 revision 等机制。连接不必机械地按每个模型请求重新创建，也不能只以服务名字相同就假定可以复用。

模型可见工具列表还要经过配置与策略过滤。enabled_tools、disabled_tools 可以收窄能力；服务的 required 设置会影响初始化失败的处理。工具发现、工具对模型可见、工具当次可执行，是三个不同条件。目录缓存可能已有工具描述，但真正调用仍需要就绪的连接和有效权限。

6.3 工具目录如何影响上下文？

工具名、描述和 schema 也占输入预算。工具很多时，可以采用增量发布、目录搜索、按任务暴露能力，或程序化调用的工具发现层；公开快照存在增量工具上下文、目录缓存及 code-mode 等机制。不能假定每次请求都携带所有 MCP 工具，也不能假定模型看见一个名字就拥有完整 schema。

远程 MCP 的写入可能发生在远端业务系统。只给本地 shell 加沙箱，无法约束一个远程“删除工单”工具。因此权限需要贯穿宿主和服务端。服务返回的 isError、结构化内容、图片或资源引用，也需要宿主映射为模型可消费的结果；一次调用成功返回，并不必然表示业务目标已完成。

优点

统一接入与工具发现；模型与业务适配解耦；可复用认证和服务；数据按需读取；具备较明确的协议边界。

缺点与防线

schema 膨胀、网络和认证失效、服务版本变化、恶意描述与返回内容、远端副作用。应隔离凭据、限制工具、保留来源，按风险设计幂等与审计。

07 / COORDINATION WITHOUT A SHARED BRAIN

子 Agent 与多 Agent：把上下文分开，再把结果汇合

一个子 agent 是拥有独立执行循环和会话状态的工作者。多 agent 协作依靠任务、消息、状态和成果交换；各 agent 不共享同一个连续思维流。

7.1 三种并行不要混淆

方式并行的对象上下文适合任务
并行工具多个独立工具执行同一主 agent 继续消费结果批量文件读取、独立 API 查询
程序化工具编排模型生成代码，由工具 Runtime 组合多个调用主模型可只接收显式输出的聚合结果大量结构化数据处理、减少中间输出
多 Agent多个模型上下文与执行循环各自独立，通过消息和最终结果连接独立调查、不同专长、可分离的实现与验证

7.2 子 Agent 如何获得上下文？

常见策略有三种：继承当前历史快照，降低任务背景缺失；只传任务与必要背景，减少污染与成本；选择性继承，保留约束、关键消息和证据入口，过滤噪声。具体 API 名称、过滤规则和默认行为随运行版本变化。

公开实现 中，spawn 负责派生配置、解析父线程、处理权限与环境继承、准备历史和初始输入。代码存在按消息类型和 phase 过滤继承内容的路径，并移除旧的角色提示等片段，避免把“你是父 agent”错误带给子 agent。因此“继承完整历史”也需要按具体实现理解，不宜断言逐字继承所有工具、推理和运行句柄。[C13]

7.3 协作 Runtime 的核心组件

  • 生命周期：创建、运行、等待输入、完成、失败、中断和卸载；父线程不能把 spawn 成功误认为子任务完成。
  • 任务与消息：传递目标、资源范围、输出契约和修改约束。消息应带发送者、接收者、任务 ID、回复关系与状态。
  • 调度与预算：控制并发槽位、深度、等待超时和累计成本；需要防止递归拆分无限增长。
  • 邮箱与唤醒：运行中的 agent 在安全边界接收输入；空闲者可以被任务唤醒。源码中有卸载会话的待收邮箱，以及运行容量和状态监视组件。
  • 结果归并：父 agent 收集结论与证据，检查冲突、验证适用版本，再决定最终答复或集成修改。

公开源码可见 agent/control 的 spawn、mailbox、budget、watch 等模块，及 inter-agent 记录类型。官方文档讨论了通过独立上下文减少主线程噪声的价值。[C13][D9]

7.4 文件系统与授权不是天然隔离的

独立上下文只隔离模型输入。若多个 agent 共享目录，同时编辑同一文件仍会冲突；即使文件不同，也可能修改同一接口或依赖。可选策略包括文件所有权、串行集成、独立 Git worktree、固定提交作为验证输入，以及明确的合并负责人。Worktree 隔离 Git 工作状态，但不等同于安全沙箱。

子 agent 的工具与权限由运行时配置派生，不能通过提示词自行升级。某个 agent 的“请帮我发送消息”也不等于人类用户授权了外部发送。协作消息与外部内容都应保留来源，禁止把总结中的推测变成新的权限事实。

7.5 性能：更快的条件是什么？

串行耗时 ≈ Σ 子任务耗时
理想并行耗时 ≈ max(独立子任务耗时) + 启动 + 协调 + 汇总 + 集成 + 依赖阶段

这只是分析模型。真实收益受共享配额、工具资源、依赖和冲突影响。继承大历史会复制逻辑输入成本；缓存有机会减少重复计算，但不会让多个 agent 免费。主线程 token 可能减少，整个任务总 token 却增加，应同时衡量总成本、延迟和完成质量。

值得采用

可独立的只读探索；多个互补审查角度；证据范围不同的调查；按模块可隔离的实现；有明确产出和整合人的任务。

容易得不偿失

每一步都依赖上一结果；共享文件频繁改写；主任务太小；分工不清；所有 agent 重复搜索同一资料；用投票替代真实测试。

08 / BUILDING YOUR OWN HARNESS

从可用闭环到可恢复系统：实现顺序与取舍

如果要实现一个类似 Codex 的 harness，应先让状态边界清楚、工具结果可靠，再增加长上下文、长期记忆和多 agent。复杂功能会放大基础状态模型的问题。

8.2 优先建立的实现不变量

  • 合法的模型历史：调用与结果能匹配；保留角色、phase、类型和多模态字段；裁剪不制造孤立协议项。
  • 明确的完成状态：模型流结束、工具执行完、回合完成、用户目标完成分别表达。
  • 可恢复边界：检查点足以重建模型窗口与必要宿主状态；后台安装不会覆盖新输入。
  • 可追溯记录：每个工具动作关联 thread / turn / call / execution ID，必要时连接业务操作 ID。
  • 工作区真实：聊天摘要中的结论与当前文件、提交和外部系统相互核对；回退对话不伪装成回退世界。
  • 权限单调受控：模型、记忆、外部内容与子 agent 消息不能自行升级权限。
  • 预算可解释：区分当前窗口、累计 usage、压缩开销、缓存命中和全体 agent 总消耗。

8.3 五个阶段的建设路线

阶段应实现验收问题
① 最小闭环结构化 items、工具验证、流式输出、权限、取消与完成语义工具报错后能否修复？能否区分进度和交付？
② 持久会话规范记录、回放、当前配置、分页与查询投影重启后能否正确继续？写入中断如何处理？
③ 上下文工程来源处限流、预算检查、压缩检查点、检索和精度恢复压缩后能否保留用户最后一次纠正与未完成事项？
④ 跨任务记忆异步提取、整合锁、范围与出处、纠正与删除路径是否误把单次要求推广为长期偏好？
⑤ 多 Agent委派契约、邮箱、调度、隔离、集成与总成本评测相比单 agent，是否更快或更准，且成本可接受？

8.5 真正有价值的评测

除了任务成功率，还应观察：压缩后约束保留率、恢复后下一步正确率、过期记忆误用率、工具重复副作用、取消延迟、历史读取延迟、总 token 与用户等待时间。不要只比较一次模型回答的质量。

上下文与恢复测试

在压缩前后插入用户纠正；在检查点写入和投影更新之间中断；让一个工具调用完成但回执丢失；fork 后继续写父线程；更换模型窗口；恢复时更改工作区。检查它是否保持目标、边界和事实。

记忆与协作测试

用“仅这次如此”测试范围；用新事实覆盖旧结论；让外部文档夹带指令；给子 agent 冲突信息；让两个 agent 修改同一接口；在共享限流下比较单 agent 与并行方案。

最终设计准则：让模型只承担必须依靠语义判断的部分；让 Runtime 明确执行状态转换；让证据保留在可访问的来源；让上下文成为有预算、可恢复、有来源的工作视图。
